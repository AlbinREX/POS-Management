# Phase 3 verification

**Result: PASS.** Implementation and full verification ran on 2026-09-11; Docker recovery was rechecked on 2026-09-12. Scope is restaurant layout only. Orders, KDS execution and Payments were not started.

## Implemented

- Configurable Area records, with arbitrary names, descriptions, ordering, active/archive lifecycle and canvas dimensions. Indoor and Terrace are editable name examples in the creation form, not fixed types or automatically seeded business data.
- RestaurantTable records with branch-unique number, name, capacity, area, position, width, height, rectangle/square/circle shape, status, active flag, version and lifecycle timestamps. Composite foreign keys enforce branch and organization scope.
- A visual SVG floor plan in the existing admin app: area selector, status legend/text, zoom, map scrolling, table selection/list, explicit arrange mode with drag-to-save, numeric geometry editing and guarded status/archive actions.
- Backend layout.read, layout.manage and layout.status.manage permissions. Fresh role defaults and the audited protected-owner upgrade preserve the existing authorization architecture and all other installed role grants.
- Serializable changes with optimistic versions, geometry/overlap/dependency checks and immutable before/after audits. Audit or event failure rolls back the entity, version and branch revision together.
- LayoutRevision and immutable LayoutEvent records, a branch-scoped replayable change feed, and coherent map snapshots. The admin checks the feed every five seconds, visibly pauses editing on connection failure, and recovers by reloading authoritative state.

The complete status vocabulary is FREE, OCCUPIED, ORDER_SENT, WAITING_PAYMENT, RESERVED and DISABLED. Phase 3 only permits FREE ↔ RESERVED and FREE ↔ DISABLED. Order-related states cannot be assigned through this API. Reservation is a manual availability marker, without booking/customer/time data. Realtime-ready persistence and polling are implemented; WebSocket push delivery is not claimed.

## Issues found and fixed

- The initial mobile drag test attempted pointer movement below the phone viewport. The test now scrolls the SVG table into view before taking coordinates; desktop and mobile reruns pass.
- Screenshot review found the mobile area selector too narrow beside its buttons. It now occupies a full row on small screens; the deployed smoke test verifies its width exceeds 300 pixels at a 390-pixel viewport.
- Reading the paginated area list before advancing to a newer map revision could skip an area created during loading. The client now reads the map revision first, then the area list, so racing changes remain replayable. A regression test deliberately returns an old area list after a concurrent area creation and verifies the new option appears on the next refresh.
- Initial schema validation required a composite unique key for the one-to-one branch revision relation; corrected before migration execution.
- Docker was unavailable on resuming the task on 2026-09-12 because the daemon was stopped. Starting Desktop and the stack restored service without changing application code or rebuilding images.

Existing non-failing tooling warnings remain: Vitest's future Vite native-config warning, pg's concurrent-query scheduling deprecation in the existing foundation authentication path, and Playwright's NO_COLOR/FORCE_COLOR precedence warning. Windows PowerShell may label Docker's stderr progress as NativeCommandError in captured output despite exit code 0; actual exit status, services and HTTP responses were verified separately. No warning was counted as a passing functional assertion or silently suppressed.

## Limitations and next boundary

This remains a local-server-dependent foundation. Actual WebSocket delivery, cloud synchronization, event retention/pruning, scheduled reservations, waiter assignment, open-order operations and financial workflows are deferred. Events are retained without pruning; future retention needs a replay-gap contract. No physical mobile device, venue-scale load, WAN-isolation or power-failure SLA is claimed. The current loopback HTTP configuration is for evaluation; production LAN use still requires documented trusted HTTPS and the remaining hardening phases.

Phase 4 may begin only after separate user authorization. No Orders, KDS or Payments implementation was added.
