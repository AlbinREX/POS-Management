# Phase 12 verification: offline and local-first hardening with outbound sync

Verified locally on **2026-09-16**. Scope is Phase 12 only. Phase 13 was not started.

**Phase 12 is complete.** Every gate passes: lint, typecheck, 127 unit tests, 165 integration checks, 26 browser tests, the production build, deployed-container verification through Nginx, migration-from-zero, and the restart-recovery and sync outage/recovery drills. One regression introduced by this phase was found by controlled experiment, diagnosed by direct measurement and fixed; it is recorded in full below, including four hypotheses that were tested and disproven.

Phase 12 hardens operation without the public internet, makes the connectivity and delivery states legible, and adds a durable delivery checkpoint for an optional cloud consumer. It adds no offline ordering and no client write queue, and this document states that boundary explicitly rather than leaving it implied.

## Implemented

- One new table, `SyncCheckpoint`, recording per branch and stream how far an optional cloud consumer has confirmed delivery, with the last attempt and delivery times, the last error and a failure count. It holds no business data and is never a source of truth.
- A `sync.read` permission and a read-only `GET /api/sync/status` reporting, per branch, the locally committed revision, the delivered revision, the pending backlog and the last error for all seven durable event streams.
- A delivery worker running on its own timer outside every request and business transaction, inert unless `SYNC_TARGET_URL` is configured, with exponential backoff to five minutes and a re-entrancy guard.
- A compact header indicator distinguishing restaurant server connected, restaurant server unavailable, no internet, and the cloud delivery health, in the existing charcoal and gold design.
- A shared client connectivity module that standardizes how the surfaces classify a failure: a rejected request carrying an HTTP status proves the server answered, so only a request that never completed means the local server is unreachable.
- Runtime grants that let the runtime role advance the checkpoint but never delete or truncate it, and CHECK constraints restricting the stream to the seven known logs and keeping the cursor and failure count non-negative.

## Queued versus non-queued commands

**Nothing is queued.** No command is held on a device for later delivery, in any surface, including the waiter PWA.

| Command class                                 | Queued offline | Why                                                                                              |
| --------------------------------------------- | -------------- | ------------------------------------------------------------------------------------------------ |
| Order create, item add/void, discount, cancel | No             | Totals, table state and kitchen locks are validated against authoritative branch state at commit |
| Kitchen submission and ticket transitions     | No             | All-or-nothing routing depends on current station configuration                                  |
| Payment collection, reversal, refund          | No             | Settlement is the only path to PAID and is serialized against the order and drawer               |
| Cash shift open, movement, close              | No             | Requires the actor's own open shift on an active POS terminal                                    |
| Company account charge                        | No             | Credit limit is enforced by a deferred database constraint a partitioned device cannot evaluate  |
| Stock movement, receiving, purchase orders    | No             | Ledger signs and overreceiving limits are enforced at commit                                     |
| Menu, layout and configuration edits          | No             | Expected-version commands; a stale version must be refused, not merged                           |

The existing recovery path is unchanged and remains the correct one: the exact command, with its `commandId`, is held in scoped `sessionStorage` before sending and retried explicitly after an uncertain response, including after a reload. Replaying returns the original receipt rather than duplicating the effect.

## Sync integrity coverage

The sync integration group asserts that the status endpoint requires a session and `sync.read` while a sync reader holds no operational authority and a cashier is refused entirely; that revocation takes effect on an existing session immediately; that the query is strict and rejects a client-supplied branch or organization, an unknown stream and any write method; that a real committed business write advances the local cursor and becomes pending rather than being silently acknowledged; that a delivered cursor never rewinds and that reading or checkpointing changes no order, payment, stock, ledger, audit or event row; that a checkpoint ahead of local history reports an empty backlog rather than a negative one; that a recorded delivery failure is reported as failed rather than healthy while local writes still succeed; that checkpoints and revisions never cross a branch boundary; and that the database itself refuses an unknown stream and a negative cursor.

## Resolved verification failures

One real regression was introduced and fixed; the rest were faults in new verification fixtures, not in application behaviour.

The sync indicator originally probed `organization` for sessions without `sync.read`, to test local reachability. A cashier may not read that endpoint, so the browser logged a 403 and the existing payments browser test, which asserts an empty console, failed. That was a genuine regression from this phase. The indicator now probes the public `health/ready` route, which proves the server is reachable without depending on any permission the session may not hold. The existing test was not weakened.

The first integration run failed the ahead-cursor assertion. Branch revisions in the verification database deliberately exceed `Number.MAX_SAFE_INTEGER`, with the kitchen stream at 9,007,199,254,741,004, so the hard-coded 999,999,999 cursor chosen as "ahead" was in fact far behind local history. The fixture now derives the value from the live local revision, and a further check asserts that a genuine quadrillion-scale backlog clamps to 1,000,000 for display while the cursors remain exact decimal strings.

The migration-from-zero proof twice asserted the wrong thing about the CHECK constraints. It first attempted an invalid INSERT selected from `Branch`, which inserts no rows on a freshly migrated database and therefore proved nothing; it then matched the stream list as `::text` when PostgreSQL renders a VARCHAR IN-list as `::character varying`. It now asserts both constraint definitions directly, and the integration suite exercises the actual rejection against seeded data.

The mobile browser regression is recorded in full, including four hypotheses that were tested and disproven, because the sequence shows why the final cause is the right one.

The Phase 9 mobile companies spec, untouched by this phase, began timing out after 90 seconds while clicking Save in its modal, having passed in about two seconds under Phases 10 and 11. A control run with this phase's client changes reverted passed the entire gate, establishing that the regression was introduced here. A second, narrower control removed only the rendered indicator element while leaving its stylesheet in place, and the gate passed again, isolating the trigger to the rendered element rather than the CSS.

Four hypotheses were tested and disproven. Render churn from the fifteen-second poll was a genuine defect, since the component replaced its whole status object on every response and `serverTime` differs each time; it was fixed, and the failure persisted. Header height from `white-space: nowrap` was addressed by capping and ellipsizing the indicator below 640 pixels; the built stylesheet confirmed the rule applied, and the failure persisted. Live-region semantics were removed entirely, leaving the element rendered without `role="status"` or `aria-label`, and the failure persisted, which is consistent with Playwright's actionability checks never consulting the accessibility tree. A reduced element carrying the class but no children passed, and the same element with purely static children that never change after mount failed, which ruled out every update-driven explanation.

The cause was then measured directly rather than inferred. At the 390-pixel mobile viewport the document reported a scroll width of 473 against a client width of 390: the header's right-hand flex row, which holds the signed-in user and the sign-out button, had no spare width, so adding the indicator pushed the document wider than the layout viewport. An overflowing page in mobile emulation is rescaled, so `innerWidth` became 473 while the visual viewport stayed 390, every client coordinate shifted, the modal's target drifted under each retry, and the element-stability check never settled. The trace corroborated this with 98 screencast frames in the final 60 seconds at a median gap of 516 milliseconds, a page repainting continuously rather than resting.

The fix is that the indicator is not rendered below 640 pixels. After it, the same measurement reports a scroll width of 390 against a client width of 390 at scale 1, and the mobile companies spec passes in 1.9 seconds. The connectivity and sync state remain available on the Owner/Admin dashboard, which is where the technical detail belongs, and the desktop header is unchanged. The sync browser spec now asserts the indicator's content on desktop and, on mobile, asserts both that it is absent and that the document does not exceed the layout width, so the regression is guarded rather than merely avoided. No test was weakened, skipped or given a longer timeout.

The new sync browser spec asserted an empty console while deliberately aborting requests to prove the unavailable state, which the browser necessarily reports as `net::ERR_FAILED`. Those two requirements contradict each other. The spec now uses the convention already established by the payments, orders and inventory specs, gating the console collector with a `networkTest` flag around the fault window, and it aborts the routes the indicator actually probes, `sync/status` and the public `health/ready`, rather than the endpoint it probed before the regression fix above. The assertion itself was not loosened.

The deployed check posted an area through the command helper, which injects a `commandId`. `areaInputSchema` is strict and the layout controller parses the raw body, so the unknown key was correctly rejected with a 400. The fixture now posts the plain body, matching how every integration suite creates an area.

## Known limitations

- **No offline ordering and no write queue.** The restaurant operates without the internet, not without its local server. This is deliberate and explained above.
- **The cloud transport is not implemented.** No cloud endpoint is specified or certified for this system. With `SYNC_TARGET_URL` set, the worker records an explicit transport-not-implemented failure rather than marking records delivered that no consumer received.
- **Cloud-to-local application is out of scope.** Delivery is outbound only, which is what makes destructive overwrite impossible in this phase.
- **No WebSocket push.** Clients continue to poll authoritative local reads.
- **`navigator.onLine` is advisory.** It reports link-layer state and can claim connectivity behind a captive portal, so it is never used to decide whether local operation may proceed.
