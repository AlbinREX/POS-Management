# Phase 11 verification: reporting and owner dashboard

Verified locally on **2026-09-16**. Scope is Phase 11 only. No offline synchronization, fiscalization or Phase 12 work was started.

**Phase 11 is complete.** Every gate passed: lint, typecheck, 115 unit tests, 156 integration checks, 24 browser tests, the production build, deployed-container verification through Nginx and migration-from-zero. One pre-existing Phase 9 schema drift is documented under known limitations; it predates this phase and was deliberately not changed here.

Phase 11 requires separate authorization under `docs/ROADMAP.md` and `docs/PHASE_10_VERIFICATION.md`. The operator gave that authorization explicitly in this session, requesting a transaction-backed reporting API and an owner dashboard that read the existing authoritative records without weakening any Phase 1-10 guarantee, and preferring no schema migration if reporting can be derived safely from existing data.

## Implemented

- A read-only reporting API under `/api/reports`, every route a GET behind the single new `report.read` permission: overview, sales, orders, products, staff, cash, inventory, purchasing, companies, and a CSV export for each of the eight report kinds.
- An owner dashboard as the **Dashboard** tab of the existing Riza frontend, with the dark charcoal, black and gold palette, KPI cards, drill-down tables, inline CSS bar series for the daily and hourly figures, and explicit loading, empty and error states.
- Date range controls for Today, Yesterday, This week, This month and a custom inclusive span, resolved in the branch's own calendar from `Branch.timezone`, with every response echoing the resolved range, its timezone and both UTC instants.
- Sales figures recognized at settlement time: gross, discounts, sales after discount, tax, net excluding tax, order count, average order value, dine-in versus takeaway, payment mix by method, and COMPANY_ACCOUNT totals. Refunds and cancellations are reported as their own lines on the day recorded and never restate the original sale.
- Product and category revenue derived from the trigger-frozen `OrderItem` snapshots with voided lines excluded, so a later price change cannot alter historical revenue. Modifier usage is counted and never summed into revenue, because modifier price adjustments are already folded into line totals.
- Staff figures limited to what the schema records: settled orders attributed to a waiter snapshot with order count, sales, average ticket and dine-in/takeaway split, and settlements performed by each cashier. No hours, speed or tip metric was invented.
- Cash reporting over the signed `CashMovement` ledger: opening float, cash in, cash out, cash sales, reversals, expected versus counted and the difference, reading a closed shift's stored figures and computing an open shift's running expectation.
- Inventory reporting derived from `SUM(StockMovement.quantity)` per position using the inventory module's own low-stock rule, with negative stock derived from the same sum. No second balance table was introduced.
- Purchasing and company reporting as the signed `SupplierEntry` and `CompanyLedgerEntry` sums, with overdue amounts taken from immutable `CompanyStatement` due dates rather than recomputed from current contract terms.
- CSV export as the first non-JSON response in the API: RFC 4180 quoting, formula-injection neutralization, a UTF-8 byte-order mark, `Content-Disposition: attachment`, and a refusal above 50,000 rows rather than silent truncation.
- One data-only migration. No table, column, index, constraint or trigger was added or altered.

## Reporting integrity coverage

The eleven reporting integration groups run against a dedicated branch whose every figure is known exactly, plus the main branch already populated by every earlier suite. They assert that reports require a session and `report.read` while a report-only account is refused orders, payments and companies and a CASHIER is refused every report; that the range schema rejects a client `branchId` or `organizationId`, a custom range without dates, an inverted range, a span above 366 days and an unknown report kind, and that no write route exists; that sales KPIs reconcile to the cent against the immutable order and payment records, with a voided line excluded, a discount applied, a cancelled order excluded and a refund reported separately; that product revenue comes from frozen snapshots and does not move when the product's price is later raised; that cash shifts report their stored counted and difference figures after closing and their computed expectation while open; that inventory, purchasing and company figures equal the operational endpoints; that presets and custom ranges resolve on the branch calendar and exclude other days; that CSV exports carry exact values, the correct header row, `text/csv` and an attachment filename, and that a negative ledger figure is protected from formula interpretation; that the main branch never sees the reporting branch's companies, suppliers, stock, shifts, waiters or tables; that every supplier, company, stock position and shift on the populated main branch matches its own account or shift endpoint; and that a full pass over every report and export leaves every ledger, order and audit row count unchanged while revoking the key stops reads immediately.

## Known limitations

- **No branch selector.** A session binds one branch and no cross-branch read permission exists, so the dashboard reports the signed-in branch and displays its identity. Multi-branch consolidation would need its own permission and isolation tests and was not approximated.
- **Payment mix is by tender time, sales by settlement time.** Over an open period the two can differ by a partial payment collected before its order settled; over any closed period they reconcile.
- **No PDF export.** No rendering tooling exists in the repository, so only CSV is produced.
- **Staff metrics are limited to recorded facts.** Preparation speed, hours worked and tips are not in the schema and are not reported.
- **Order status counts are by creation date** while revenue is by settlement date, so an order created before a range and settled inside it appears in revenue but not in that range's status counts. Both are labelled in the API contract.
- **Exports are capped at 50,000 rows** and refuse rather than truncate; a larger period must be exported in narrower ranges.
- **A pre-existing schema drift predates this phase and is not resolved here.** `prisma migrate diff` from a fully migrated database to `schema.prisma` exits 2, reporting index and foreign-key name truncations on the Phase 9 `CompanyEmployee`, `CompanyLedgerEntry`, `CompanyStatement` and `Payment` tables plus one `Payment` index. Applying only the ten pre-Phase-11 migrations to a throwaway database reproduces the identical diff, so this drift comes from the Phase 9 migration SQL and not from Phase 11. Phase 11 neither introduced nor corrected it; correcting it needs its own migration and authorization. Evidence: `.local/phase11-baseline-drift.json` and `.local/phase11-migrate-from-zero.json`.

## Resolved verification failures

Every failure in this phase was in the new test fixtures or in result ordering, not in reporting arithmetic or in any Phase 1-10 guarantee.

The reporting fixture first opened a cash shift, settled a cash order against it and then issued a drawer command with the stale shift version it had captured before the settlement, which the optimistic version check correctly rejected with a 409. The fixture now re-reads the shift before the drawer commands. It then posted a goods receipt with an invoice number but no invoice date, which the purchasing schema correctly rejects because the two are required together; the fixture now supplies both. It also created a branch membership for a user the API had already made a member of the session's branch, violating the membership primary key; that redundant seeding was removed. A statement fixture covering only the current day collided with a period another suite had already issued, so it now covers a two-day period.

Three reports ordered their grouped rows with a Prisma `orderBy` on an enum column, which sorts by PostgreSQL enum declaration order rather than alphabetically, making the asserted row order depend on the enum definition. Those now sort explicitly by name in TypeScript, which is stable and matches what the tables display.

Docker Desktop was found stopped partway through the deployed verification, so the first image rebuild and the pre-migration backup both failed to reach the daemon. No container or database work had been applied at that point. The daemon was restarted from its per-user install path, the backup was taken successfully and the rebuild was repeated.

The mobile inventory browser test, a Phase 7 spec untouched by this phase, timed out once at 90 seconds while waiting for its navigation button. Its failure snapshot showed the page still rendering the initial `Connecting to your restaurant…` state, which the application shows while the session restore is in flight, so the shell had never rendered and no locator could have matched. It was a harness startup stall rather than a layout or navigation regression: an added navigation entry would have scrolled into view rather than disappeared, because the navigation is `overflow-x: auto` at mobile width and Playwright scrolls to a locator before clicking. The spec passed in 2.3 seconds on the next run with no change to it, to its startup path or to any application code, and the full gate then reported zero failures. The test was not weakened, retried in-place or skipped.

The first browser run failed one assertion in the new reporting spec. The spec clicked through all seven report views in a loop, which ends on Companies, and then asserted on the Products table, which was no longer rendered; Playwright correctly reported the table as not found. The spec now re-opens Products immediately before that assertion. No dashboard or reporting behaviour was changed to make it pass.

The schema-drift proof was written twice against removed Prisma flags before it ran. `--from-url` and `--to-schema-datamodel` no longer exist in this Prisma version, and `--from-migrations` requires a configured shadow database. The proof now uses `--from-config-datasource --to-schema` against the freshly migrated throwaway database, which needs no shadow database. Its result, and the baseline comparison attributing the reported drift to Phase 9, are recorded under known limitations above.
