# ADR 0003: Branch-owned layout and durable change events

Status: accepted for Phase 3.

Area and RestaurantTable extend the local PostgreSQL/NestJS architecture. Areas have arbitrary names; Indoor and Terrace are editable UI examples, not seeded business entities or fixed area types. Each area defines an integer canvas size in layout units. Tables have branch-unique numbers, capacity, position, size and RECTANGLE/SQUARE/CIRCLE shape. Squares and circles require equal width and height. Names and numbers remain reserved after archival.

All relationships carry branch and organization composite foreign keys. Area/table modifications use optimistic versions, serializable transactions, soft deletion and allowlisted audit snapshots. Tables must fit the area's canvas. Bounding boxes cannot overlap other unarchived tables; disabled tables still occupy physical space. Resizing an area cannot clip existing tables. Moving a physical table between areas requires it to be FREE or DISABLED; no order transfer/merge is implemented.

The status vocabulary includes FREE, OCCUPIED, ORDER_SENT, WAITING_PAYMENT, RESERVED and DISABLED. Phase 3 permits FREE ↔ RESERVED and FREE ↔ DISABLED only. Reservation is a manual marker with no booking/time/customer record. Active is derived from status (DISABLED is inactive). Order-related states are reserved for later transactional order workflows and cannot be assigned by this API. Reserved tables must be freed before disabling, moving or archiving. An area must have all remaining tables disabled before deactivation, and all tables archived before archival. Inactive areas cannot receive new tables or active status changes.

Permissions are layout.read, layout.manage (area/table configuration, geometry and archives), and layout.status.manage (permitted status changes). Every mutation also requires layout.read. Fresh OWNER/ADMIN receive all three; MANAGER receives read/status. Existing protected owners receive the new keys through an audited migration; all other existing role mappings remain unchanged. There is no role-name bypass or frontend-provided branch scope.

Each successful mutation increments a branch LayoutRevision and appends an immutable LayoutEvent in the same transaction as the business change and AuditLog. Events are invalidations, not authoritative state or financial records. Their branch revision is a decimal string over JSON to preserve BIGINT precision; it is committed in branch order, indexed and unique. Reads expose an authenticated paginated change feed and a repeatable-read area/map snapshot with its revision. Clients refresh authoritative state when an event arrives and resume from a cursor after disconnection. The admin checks the feed every five seconds, including current permissions on each request. Offline/stale state is visibly marked and editing is disabled until a successful snapshot reload.

This is realtime-ready persistence, not a WebSocket delivery claim. A future authenticated WebSocket gateway can read this durable feed, authorize branch subscriptions, replay after the last cursor, and send invalidations at least once. Clients must deduplicate by event ID/revision and refetch after gaps. No cloud dependency, in-memory-only event bus, SSE transport or naive last-write-wins scheme is introduced. Events are retained without automatic pruning in this phase; retention will require a replay-gap contract.

The map offers an explicit arrange mode for pointer dragging and numeric position/size inputs for precise keyboard/mobile editing. A drag commits on release, not on every pointer movement. Status colors also have text labels. List endpoints paginate; map snapshots contain all unarchived tables in the selected area and are not silently truncated. Area/table counts and venue-scale load should be measured before a commercial rollout. No Orders, KDS, Payments, waiter assignment, reservation scheduler or financial logic is implemented here.
