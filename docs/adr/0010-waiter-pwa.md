# ADR 0010: waiter PWA as an installable route of the existing frontend

Phase 10 adds a mobile-first waiter surface. It introduces no database table, no migration, no permission key and no business rule. Every order, table, kitchen and payment guarantee from Phases 1-9 remains the single authority; the PWA is a client over the existing API.

The waiter surface is served at `/waiter` by the existing Next.js deployment, exactly as Phase 5 serves the kitchen display at `/kds`. A dedicated route reuses the established authentication, refresh-cookie session restore, `/api` proxying, CSP and Docker/Nginx topology without duplicating any of them, and keeps `apps/waiter/` reserved for later independent packaging. A separate application would have required extracting the API client and Riza primitives into a shared package, a second server in the browser harness, another Playwright project and new Docker, Compose and Nginx targets — more places for branch isolation and session handling to diverge, for no functional gain at this scale.

No permission key is added. `WAITER` already holds `menu.read`, `layout.read`, `order.read`, `order.manage` and `order.submit_kitchen`. Requesting payment is an ordinary order command whose transition is validated server-side, so a waiter moves an order to WAITING_PAYMENT with `order.manage` and never holds a payment key. Collection stays behind `payment.read`/`payment.collect` with the cashier, and a company account charge continues to require `company.charge` under the Phase 9 rules. The waiter surface therefore cannot discount, cancel, reassign another waiter, read the kitchen display or settle money, and the server enforces that independently of what the client renders.

Ordering reuses the existing order workspace in its touch-oriented mode rather than reimplementing a cart. Categories, product search, images with fallbacks, modifiers, quantities, item and order notes, permission-gated discounts, totals, immutable product/price/tax/modifier snapshots, optimistic versions, the five-second authoritative refresh, the stale-read write lock and the sessionStorage retry receipt are the same implementation the POS uses. A second cart would have been a second place for money and snapshot rules to drift.

The table view is the one genuinely new component. A table record carries no order reference, so the live order for a table is resolved from the branch order list by table identifier, restricted to non-terminal states; one live order per table is already enforced by a partial unique index. Table status uses the same vocabulary and colours as the floor plan, including the order-driven OCCUPIED, ORDER_SENT and WAITING_PAYMENT states that only the server sets. The durable layout change feed and its branch revision cursor drive refreshes, so the waiter sees the same authoritative state as the manager.

Kitchen submission remains all-or-nothing. A submitted order rejects every further command except cancellation and the ready-to-waiting-payment transition, and the PWA presents that rather than working around it: a sent order is shown as locked, and more items mean a new order for the table. Adding a second round would require an amendment protocol with its own integrity guards and is deliberately out of scope, because silently loosening submitted-content immutability would weaken Phase 5.

The service worker precaches the application shell only. Every `/api/` request bypasses the cache entirely, so no authenticated, branch-scoped response is ever stored on a shared device or replayed stale at order time. This makes the app installable and fast to launch; it is not offline ordering. Without the local server the app reports an explicit connection failure instead of accepting work it cannot commit, and no write is ever queued. Offline behaviour, conflict resolution and synchronization remain Phase 12. Service workers require a secure context, so an installed PWA on a LAN host needs the documented TLS deployment; plain HTTP works only on loopback.

The content security policy gains explicit `worker-src` and `manifest-src` directives. Both were already satisfied by the `default-src 'self'` fallback, but relying on a fallback means a later tightening of `default-src` would disable the service worker silently.

Out of scope: offline ordering and write queues, kitchen amendments, payment collection from the waiter device, push notifications, background sync, table transfer or merge, split-by-seat, and fiscalization.
