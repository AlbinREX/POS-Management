# ADR 0005: transactional kitchen tickets

Phase 5 adds one immutable submission per OPEN order. Each nonvoid item routes to every station currently configured on its source product. Missing, archived or inactive stations reject the whole submission; no fallback station or silent omission. Product availability/pricing is not reread: names, quantities, modifiers and notes come from existing order snapshots. Routes and station names are frozen at submission. Multiple stations each receive the full item quantity, not a divided quantity.

KitchenSubmission, KitchenTicket and KitchenTicketItem reference source orders/items through composite branch/organization keys. Ticket content is an allowlisted immutable JSON snapshot with a versioned printer contract. It omits prices, discounts, customer financial data and permission information. No ESC/POS commands, network printer access, spool worker or claim of physical printing is introduced. Ticket IDs plus event revisions are delivery deduplication identifiers for a future printer adapter; cancellation has its own contract kind.

Tickets progress NEW -> PREPARING -> READY -> COMPLETED with expected versions and idempotent command IDs. COMPLETED means cleared/collected from the kitchen, not paid or served. All tickets ready/completed makes the order READY; any progress before that makes it PREPARING; all NEW means SENT_TO_KITCHEN. Submission marks its table ORDER_SENT. Requesting payment from READY keeps existing payment-free WAITING_PAYMENT semantics. Cancelled tickets retain the last preparation status and carry cancellation time/reason, including tickets previously completed, so history never disappears.

Submission freezes order items, modifiers, notes, waiter identity and totals. Order cancellation and requesting payment after readiness remain allowed. Additional rounds, partial ticket/item cancellation and edits after submission need an explicit future amendment protocol; they are not silently sent as replacements. Database guards prevent reopening a submitted order into an editable state and preserve immutable ticket content and audit/event history.

Serializable transactions commit order versions/history, tickets, branch kitchen revision/events, audit and table state together. Order submission uses the existing order command replay namespace; ticket transitions use branch-scoped kitchen command IDs with actor/hash binding and stored responses. The feed exposes monotonically committed BIGINT string revisions with authenticated replay; no last-write-wins or in-memory-only delivery. Failed transactions leave no tickets or events.

Permissions are order.submit_kitchen, kitchen.read and kitchen.manage. Kitchen users receive only kitchen read/manage defaults, no menu/order financial access. Existing mappings are preserved except the audited protected OWNER permission upgrade. Branch-scoped station lists include archived stations with outstanding tickets; disabling routing does not hide already-submitted work.

The dedicated /kds screen lives in the existing Next.js deployment and reuses its authentication; it exposes only the kitchen surface, even for owners. The regular workspace also links to Kitchen. This avoids duplicating authentication/deployment while retaining the reserved apps/kds boundary for future independent packaging. A five-second authenticated refresh, server-derived elapsed times, stale-state locking and a configurable on-screen delay threshold support local LAN operation. Uncertain commands retain a sessionStorage retry receipt. WebSocket push, printer execution, offline write queues, Payments and PAID transitions remain deferred.
